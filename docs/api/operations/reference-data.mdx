# Reference Data

Fourteen small `GET` endpoints returning the lookup lists the portal's dropdowns are built from.
They share a shape, so they are documented together here rather than one page each.

All of them:

- are `GET` under `/api/v1/web-app`, take no path parameters and no request body;
- require a [bearer token](/getting-started/authentication#bearer-tokens) plus a permission;
- return the [list envelope](/getting-started/response-format#unpaginated-lists);
- are cached server-side for 24 hours.

## Shared query parameters

Thirteen of the fourteen accept the same pagination parameters. They are **paginated by default**,
eight rows per page — which is rarely what a dropdown wants, so most callers pass `no_page=true`.

<ParamTable
  params={[
    { name: 'limit', type: 'integer', required: false, default: '8', description: 'Page size, between 1 and 200.', example: '50' },
    { name: 'offset', type: 'integer', required: false, default: '0', description: 'Records to skip.', example: '50' },
    { name: 'no_page', type: 'boolean', required: false, default: 'false', description: 'Return every row without pagination. Cannot be combined with limit or offset.', example: 'true' },
  ]}
/>

:::caution `no_page` here, `noPage` elsewhere
These endpoints spell it `no_page` with an underscore. The supplier and report endpoints spell the
same flag `noPage`. See [Pagination](/concepts/pagination).

Also note: sending `no_page=true` **together with** `limit` or `offset` is rejected with
`400 limit and offset must not be provided when no_page=true.` Send one or the other.
:::

### The response changes shape with `no_page`

| Request | Envelope |
| --- | --- |
| Default (paginated) | `{ status, status_code, message, data, links, count }` |
| `no_page=true` | `{ status, status_code, message, data }` — **no `links`, no `count`** |

A client that always reads `links.next` will fail on an unpaginated response. Branch on whether you
asked for pagination.

`/item-categories` is the exception — it takes no parameters at all and always returns the full list
without `links` or `count`.

## Example

<Tabs groupId="lang">
<TabItem value="curl" label="cURL">

```bash
curl --request GET \
  --url 'https://sandboxapi.allowmena.com/api/v1/web-app/order-status?no_page=true' \
  --header 'Authorization: Bearer YOUR_TOKEN'
```

</TabItem>
<TabItem value="python" label="Python">

```python
import os
import requests

def lookup(path: str) -> list[dict]:
    """Fetch a full reference list — dropdowns want every row, not page one."""
    response = requests.get(
        f"https://sandboxapi.allowmena.com/api/v1/web-app/{path}",
        headers={"Authorization": f"Bearer {os.environ['ALLOW_TOKEN']}"},
        params={"no_page": "true"},
        timeout=30,
    )
    response.raise_for_status()
    return response.json()["data"]


statuses = lookup("order-status")
```

</TabItem>
<TabItem value="js" label="JavaScript">

```javascript
/** Fetch a full reference list — dropdowns want every row, not page one. */
async function lookup(path) {
  const url = new URL(`https://sandboxapi.allowmena.com/api/v1/web-app/${path}`);
  url.searchParams.set('no_page', 'true');

  const response = await fetch(url, {
    headers: { Authorization: `Bearer ${process.env.ALLOW_TOKEN}` },
  });
  return (await response.json()).data;
}

const statuses = await lookup('order-status');
```

</TabItem>
