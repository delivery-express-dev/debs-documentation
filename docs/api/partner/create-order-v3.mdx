# Create Order (v3)

<Endpoint method="POST" path="/api/v3/external/orders" auth="x-api-key header" />

Submits one or more delivery orders for fulfilment by the supplier branch behind your API key. This
is the recommended version for new integrations — it accepts everything v2 does and adds pickup
instruction attachments.

Use it whenever you have a delivery to dispatch: an on-demand order is picked up as soon as a driver
is available, and an order carrying a `schedule` block is queued for a delivery window you choose.
It returns the platform order id for each order you sent, paired with your own reference.

### Pickup object

Omit `pickup` entirely and the order is collected from your branch's registered address, contact and
area. That is the normal case.

required together**. Sending some but not all is rejected, naming the ones you left out.

### Schedule object

Omit `schedule` for an on-demand order. Send it to book a delivery window.

<ParamTable
  params={[
    { name: 'delivery_time_slot_start', type: 'string', required: true, description: <>Start of the delivery window, formatted <code>YYYY-MM-DD HH:MM:SS</code>. Must be far enough ahead to allow preparation and pickup — the platform rejects a start time inside that buffer and tells you the earliest acceptable time.</>, example: '"2026-11-01 15:00:00"' },
    { name: 'delivery_time_slot_end', type: 'string', required: true, description: <>End of the delivery window, same format. Must be later than <code>delivery_time_slot_start</code>.</>, example: '"2026-11-01 16:00:00"' },
  ]}
/>

:::caution Times carry no timezone
Both fields are parsed as naive local server time. Do not append `Z` or an offset — it will fail
with `Invalid datetime format`. See [Date & time](/concepts/date-time).
:::

        }
    ]

response = requests.post(
    f"{BASE_URL}/api/v3/external/orders",
    headers={"x-api-key": os.environ["ALLOW_API_KEY"], "Content-Type": "application/json"},

## Batch behaviour

The whole batch is created inside **one database transaction**. If any order fails validation, the
transaction rolls back and **no orders are created** — you get a single `400` describing the first
failure, not a per-order result.

This is different from [Cancel Orders](/api/partner/cancel-orders), which reports a per-order
outcome. Create is all-or-nothing.

:::tip Keep batches small enough to debug
Because the error names one problem for the whole batch, very large batches are awkward to diagnose.
Sending orders in modest groups makes it obvious which one the platform rejected.
:::

## Retries and duplicates

There is no idempotency key on this endpoint, and `supplier_reference_id` is **not** enforced as
unique — resending the same payload creates a second order with the same reference.

If a create request times out and you do not know whether it landed, do not blindly retry. Instead:

1. Retry only on a `500` or a network-level failure, never on a `400`.
2. After an ambiguous failure, reconcile before resending — a duplicate reference will otherwise
   produce two live deliveries.

## Differences from the published Postman collection

:::warning The Postman v3 example body is malformed
The published collection's v3 **Create Order** example nests a second `drop-off` object *inside*
`drop-off`, and places `payment_type`, `total_amount` and `supplier_reference_id` inside that nested
object rather than at the order level.

Sent as published, that body fails with `Invalid payment type`, because the backend reads
`payment_type` from the order object, not from `drop-off`.

Use the structure documented on this page: `drop-off`, `pickup`, `supplier_reference_id`,
`payment_type`, `total_amount` and `schedule` are **all siblings** at the order level. The
collection also omits `schedule`, `item_details` and `collection_method` from its v3 example,
though the backend accepts all three.
:::
