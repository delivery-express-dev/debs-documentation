# Permissions

Permissions apply only to the [Operations API](/api/operations/overview) (`/api/v1/web-app`). The
partner, service and driver surfaces authorise by credential alone and have no permission model.

## How it works

A portal user's access token carries a `features` claim — the list of feature codes granted to them:

```json
{
  "id": 7,
  "user_type": 1,
  "features": ["read-supplier", "update-supplier"],
  "exp": 1721476800
}
```

Each endpoint declares the codes it accepts. On every request the platform intersects the two sets:

1. If the caller is the **super admin** (user id `1`), access is granted regardless of `features`.
2. Otherwise, if **any one** of the endpoint's codes is in `features`, access is granted.
3. Otherwise the request fails with `403 FORBIDDEN`.

:::note Multiple codes mean "any one of these", not "all of them"
[Get Supplier](/api/operations/suppliers/get-supplier) accepts `read-supplier`, `create-supplier`
**or** `update-supplier`. Holding any single one is enough. This is why the read endpoint behind an
edit screen is reachable by users who can only edit.
:::

## Super admin

The user whose id is `1` is treated as the super admin and bypasses every feature check. One
endpoint goes further and is reachable **only** by that user:

| Endpoint | Gate |
| --- | --- |
| [Restore to Delivered](/api/operations/orders/restore-to-delivered) | Super admin only — no feature code grants it |

## The codes

Thirty-six feature codes exist. Most follow a `verb-resource` convention — `read-`, `create-`,
`update-`, `delete-`, `restore-` — with one exception, `cancel-after-delivery`, which is
hyphen-separated throughout rather than using an underscore in the resource part.

### Codes with no endpoint in this documentation

These exist in the feature list but do not guard any endpoint documented here. They gate parts of the
legacy portal API that is outside this documentation set — see the
[coverage audit](/coverage#legacy-django-surface).

`create-role`, `update-role`, `create-driver`, `update-driver`, `create-zone`, `update-zone`,
`create-area`, `update-area`, `create-supplier_branch`, `update-supplier_branch`,
`create-supplier_branch_hour` and `read-supplier_branch_hour` all appear above only because they
also grant a reference-data lookup — none of them grants a create or update endpoint here.

## Two endpoints need only a token

[Order Sources](/api/operations/reference-data#order-sources) and
[Payment Status](/api/operations/reference-data#payment-status) declare **no** feature code. Any
authenticated portal user can read them.

## Handling 403

A `403` means the token is valid but the user is not permitted. It will not resolve by retrying or
by refreshing the token — the user's role needs the feature code granted.

```json
{
  "status": false,
  "status_code": 403,
  "error_code": "FORBIDDEN",
  "message": "You dont have sufficient permission",
  "detail": null
}
```

The message does not name the missing code. Look the endpoint up on its page here to find out which
one to request.
