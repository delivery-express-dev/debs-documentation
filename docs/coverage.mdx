# API coverage audit

This page accounts for every endpoint in the requested Postman collection and in the backend, so
nothing is silently omitted. It is maintenance documentation, not integration documentation.

**Method.** Endpoint lists were derived from the code, not from a collection export:

- The FastAPI service's route table was read from the OpenAPI document generated by the running
  application object — 37 paths, 44 operations.
- The Django service's route table was read from its `urlpatterns`.
- The Postman collection was fetched from the published documenter API and compared endpoint by
  endpoint.

## Discrepancies between backend and Postman

Seven, none of them silent — each is flagged on the relevant endpoint page too.

### 1. The v3 create-order example body is malformed

**Severity: high — the published example does not work.**

The collection's v3 example nests a second `drop-off` object inside `drop-off`, and places
`payment_type`, `total_amount` and `supplier_reference_id` inside that nested object. The backend
reads all three from the **order** level, so the published body fails with `Invalid payment type`.

Documented correctly on [Create Order (v3)](/api/partner/create-order-v3#request-body).

### 2. The order-status webhook example uses a status that does not exist

**Severity: high — an allow-list built from it will drop real events.**

The collection shows `{"name": "Picked", "slug": "picked"}`. The backend's status table contains
neither. The real values are `Picked Up` / `picked_up`. The collection's surrounding prose is
correct; only the JSON sample is wrong.

Documented on [Webhook: Order Status](/api/webhooks/order-status#differences-from-the-published-postman-collection).

### 3. Track Order's "404" example is saved with status 400

The collection's example named *404 - Order not found* carries HTTP status `400`. The v2 tracking
endpoint returns a genuine `404`. The v1
[Get Order Status](/api/partner/order-status) endpoint *does* return `400` for a missing order, which
is the likely source of the confusion.

### 4. Cancel Order's 400 body no longer matches

The collection shows `{"message": "Not a valid string.", "status": false}`. The current backend
returns `{"status": false, "message": "Invalid request"}` — the raw serializer text is no longer
surfaced.

### 5. `x-api-key` is missing from three collection requests

Cancel Order, Track Order and the v3 Create Order carry no `x-api-key` header in the collection. The
header is required on every partner endpoint; without it the request fails with `401 UnAuthorized`.

### 6. The v3 example omits capabilities the backend supports

The collection's v3 example shows no `schedule`, no `item_details` and no `collection_method`, though
v3 accepts all three. A reader working only from the collection would believe v3 cannot schedule
orders.

### 7. `estimated_time.pickup` type in the webhook sample

The collection writes it as the string `"30"`; the backend sends the number `30`. Cosmetic, but a
strictly-typed consumer would reject the real payload.

## In backend, not in Postman

Two partner endpoints are routed and live but have no collection entry. Both are documented here:

- [`GET /api/v1/external/orders/{order_id}/status`](/api/partner/order-status)
- [`POST /api/v1/external/order/delivery-price`](/api/partner/delivery-price)

### An unintended `GET` on the order collections

Worth raising with the backend team rather than documenting as a feature:

`GET /api/v1/external/orders` and `GET /api/v2/external/orders` are **routed**. Their view classes
inherit Django REST Framework's `ListAPIView` alongside `CreateAPIView`, which registers a `GET`
handler neither view overrides. The inherited handler lists `Orders.objects.all()` — it is not
scoped to the API key's supplier branch the way every other partner read is.

This documentation does **not** publish these as supported endpoints, because they appear to be an
inheritance side effect rather than an intended contract. Flagging it here so the behaviour is
reviewed.

None. Every endpoint in the published collection exists in the backend.

## Could not be verified

Three items are marked in place rather than guessed at.

### The cancel-order request schema

`CancelInternalOrderRequest` and `CancelInternalOrderResponse` live in the shared
`allow-fastapi-tools` package, published to a private CodeArtifact registry that was not reachable
during this work. The available version (0.1.13) predates both models.

Their shape was reconstructed from the service's own tests, which show `reason` as the only field
and `{}` as an accepted body. **`reason` is verified; the absence of other fields is not.** Noted on
[Cancel Order (Service)](/api/service/cancel-order#request-body).

For the same reason, the shared error classes and the `require_api_key` dependency were reconstructed
from the test suite in order to generate the OpenAPI document. The reconstruction matches every
assertion in `tests/common/exceptions/` and `tests/api/v1/routes/internal/`, so the error envelope
and status codes documented here are test-verified.

### `openingBalance` on the branch financials report

The backend's own schema gives `openingBalance` and `creditedAmount` the **same** description:
"total amount credited to the supplier branch wallet during the selected reporting period". They are
returned as separate fields, but the code does not distinguish their meaning.

This documentation reports both fields with the backend's own wording rather than inventing a
distinction. Noted on
[Branch Financials](/api/operations/reports/supplier-branch-financials#response).

### The production base URL

No production hostname is committed to the repository — it is supplied per deployment through the
`ALLOWED_HOSTS` environment variable. Only the sandbox host,
`https://sandboxapi.allowmena.com`, is known, from the published collection. This documentation uses
the sandbox host in all examples and does not guess at production. Noted on
[Base URL](/getting-started/base-url#base-url).

## Legacy Django surface

The backend repository contains two services:

| Service | Role |
| --- | --- |
| `app/` — FastAPI (`debs-core-api`) | The current service. Its 44 operations are fully documented here. |
| `backend/` + `DEBS/` — Django (Delivery Core) | The older service. Hosts the partner API, the webhooks, and a large legacy portal and mobile surface. |

The Django partner and webhook surfaces are documented in full. The rest of the Django service is
**not** documented here, and was not in scope: the request was the Postman collection's endpoints
plus the backend behind them.

For completeness, the undocumented Django route count, by module:

| Module | Route entries | What it is |
| --- | --- | --- |
| `backend/v1/urls/web_app/` | 116 | The legacy operations portal — orders, drivers, zones, areas, scheduling, dashboards, payments, companies. Progressively being replaced by the FastAPI operations API documented here. |
| `backend/v1/urls/mobile/` | 22 | The legacy driver app API — order tasks, shifts, wallet, issues. |
| `backend/v1/urls/common/` | 18 | Shared endpoints — profile, password reset, file upload, leave applications. |
| `backend/v1/urls/internal/` | 2 | `orders/{id}/assign` and `orders/{id}/cancel`, called by the FastAPI service through its Delivery Core client. |

**158 route entries.** Each entry may expose more than one HTTP method, so the operation count is
higher. Documenting them is a separate piece of work; this note exists so the gap is visible rather
than implied.

:::note Two services both answer `/api/v1/internal`
The Django service exposes `/api/v1/internal/orders/{id}/assign` and `/cancel`; the FastAPI service
exposes `/api/v1/internal/orders` and `/orders/{id}/cancel`. They are separate deployments on
separate hosts, and the FastAPI service's cancel endpoint calls Django's. The
[Service API](/api/service/overview) pages document the FastAPI one.
:::
